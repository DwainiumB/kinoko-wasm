Kinoko Brute Forcer

Search for faster TAS input sequences using the headless kinoko_host engine, then export the best one as a .rkg ghost.

GPU evaluates a whole generation of candidates at once on the GPU build of the engine -- same genome, prefix chaining and fitness, bit-identical results. Any track, character and vehicle. One iteration = one generation.
Each is a GPU race slot (~0.57 MiB). 2048 uses ~1.2 GB of GPU memory.
1 = the CPU's hill climb (mutate the best; replace it only if a child is strictly better). k > 1 keeps the best k distinct genomes and spreads children over them.
Re-runs the current best through kinoko_host and stops with an error on any difference. 0 = off.
Searches this ghost's real input stream (after the locked prefix) instead of the control-point genome: each child is the parent with a few local edits -- stick X/Y runs, moving a button/trick change by 1-2 frames, shifting a block by a frame, setting a trick direction 1-4, hop/brake/drift on or off. Reaches everything the genome can't (drift, trick direction, stickY). The genome settings below are ignored in this mode.
Start from the base shifted by these frame offsets (base[i + s] at frame i). Use several with "GPU parents kept" set to at least as many.
Evaluate this many mutations at once per iteration and keep the best of the batch -- each is a separate kinoko_host process, so this roughly multiplies throughput by however many CPU cores you give it. 1 = old behavior. Try your core count (or one less).
If this many generations pass with no accepted improvement, the search stops itself early instead of running out the full iteration count for nothing. This is a heuristic "probably converged" signal, not a proof -- a stochastic search can't rule out further improvement, it just becomes increasingly unlikely the longer nothing changes. Leave blank to always run the full iteration count.
Advanced / start-slide tuning
How far apart the tunable steering/accelerate/trick decisions are, in frames. 1 = every single frame can differ (most precise, biggest search space). 15 = one decision covers 15 frames, interpolated in between (coarser, faster to search). Use small values (1-3) for a start slide, since timing is frame-critical there.
How many frames of the attempt get simulated and scored. The countdown itself ends at frame 411 ("GO!"), but the engine only applies the start-boost calculation the moment that frame executes -- since the simulation loop stops BEFORE reaching a cap equal to max_frames, a cap of 411 would mean frame 411 never actually runs and no boost ever gets applied or scored. 412 is the minimum that captures it. Extend further (e.g. 450-500) to also score more frames of real turning after the start, not just the pre-turn straight.
Extra reward for a genuinely good start-boost charge, on top of whichever "Score by" metric is picked -- reaching the top tier (70 boost frames) adds up to 70x this value to the score. Needed because a short frame cap can't see the boosted speed that follows GO!, so without this the search has zero reason to find a real full boost and can produce a run that looks great here but never actually boosts in Dolphin. 0 = off (old behavior).
Hard requirement: reject any candidate whose boostCharge falls below this value, no matter how good it scores otherwise. The charge-to-duration mapping has a cliff at 0.94 (0.925-0.94 = only 45 boost frames, 0.94-0.95 = 70) -- the "Boost quality bonus" above only makes staying above the cliff PREFERRED, it doesn't forbid the search from drifting back below it for a small gain elsewhere. Set to 0.94 to forbid ever losing the 70-frame tier. Empty = no gate (old behavior).
Extra reward for the kart's raw forward speed at the final scored frame. Without this, a candidate can score well on cumulative position/completion while actually ending mid-spin or stalled -- erratic steering that never commits to one turn direction can look just as good as a clean, fully-committed turn that leaves the kart accelerating forward. Matters even more for segment-chained search, since the next segment inherits whatever state this one ends in. 0 = off (old behavior).
Mirror of "Minimum boost charge": reject any candidate whose boostCharge EXCEEDS this. Above 0.95 is a full burnout (0 boost frames) -- pair this with "Accelerate hold bonus" below so the search can freely push up how long accelerate is held without accidentally crossing into burnout. Empty = no gate (old behavior).
Extra reward for the total number of Countdown-phase frames spent holding accelerate, independent of the resulting charge tier -- based on community TAS knowledge that holding accelerate longer affects kart rotation/slide distance during airtime, a real effect separate from the charge-to-boost-duration formula. Set "Maximum boost charge" to 0.95 alongside this so pushing hold-time up can't accidentally burn out the charge. 0 = off (old behavior).
Only used when "Score by" is "Progress". Continuous reward for exceeding the reference ghost's own raceCompletion (the game's real, curve-aware track position), on top of the always-on floor that just stops a result from falling behind at the final scored frame. Without this, the search has no reason to pull further ahead on the track's actual curve -- it can settle for merely tying the reference there while gaining ground only on the straight-line distance metric, which can look tied or even slightly behind mid-run despite a higher overall score. 0 = floor only (old behavior).
Only used when "Score by" is "Progress". Extra reward for progress specifically along the Z axis (whichever direction the reference itself moves in Z), ON TOP OF the normal progress score -- doesn't replace credit for X/rightward movement, just lets you dial up how much a candidate is pushed to match the reference's Z progress (e.g. how far around a turn it's come) beyond what following the curve already provides. 0 = off (old behavior).
Only used when "Score by" is "Progress". raceCompletion is coarsely quantized, so when Seed and Reference are the same (or very similar) already-good file, most small mutations produce a trajectory that's essentially as good as the reference but happens to round its completion down by a unit or two purely from quantization noise -- with 0 tolerance those get rejected outright by the gate even though they're not really behind. Confirmed in practice: with 0, over half of all mutations from a good seed were rejected this way, starving the search of real candidates. 1 (default) allows a small rounding margin; raise it further if you're still seeing very few improvements from a strong seed.
Appends a record (genome, progress, completion, boost charge) for every real evaluation this run makes, across runs if you reuse the same path. Feeds tools/train_surrogate.py to build a surrogate model -- see "Surrogate model path" below. No effect on search behavior itself, just data collection. Blank = off (old behavior).
Only used when "Score by" is "Progress" and Parallel workers > 1. A model trained by tools/train_surrogate.py on a previous eval log. When set, each generation proposes a larger pool of candidates (see "Surrogate oversample" below), cheaply ranks them all by predicted progress, and only spends real engine time on the most promising subset -- the real score/gate still makes the actual accept/reject call, the surrogate just decides what's worth checking. Blank = off (old behavior, every proposed candidate is real-evaluated).
Only used when a Surrogate model path is set. How many candidates to propose per real-evaluation slot -- e.g. 8 workers x oversample 4 = 32 candidates generated and surrogate-ranked each generation, but only the top 8 get a real engine evaluation. Higher = more filtering (cheaper on average per real evaluation spent, but more surrogate-inference overhead and more reliant on the model being accurate).
"Race completion" only moves once you cross the next checkpoint -- useless for a short window, it reads identically for wildly different attempts until ~550 frames in. "Kart speed" rewards raw speed at the frame cap, in any direction. "Progress" rewards distance travelled specifically along a reference ghost's own line (needs "Reference .rkg" below) -- the right choice when you're trying to beat a specific existing attempt rather than just go fast.
How big each random tweak is when a gene gets mutated. Bigger = more exploration (can jump further from the seed, more likely to break a working attempt). Smaller = finer refinement of an already-good attempt. Try a bigger value first to explore, then re-run seeded from the result with a smaller value to polish it.
What fraction of ALL genes get a random tweak on each attempt. With 3 channels at step=1 there can be 1000+ genes, so keep this low (0.03-0.1) -- at the default 0.3 nearly a third of everything would change at once, which is too disruptive to reliably improve on a good seed.
Start the search from this ghost's actual recorded inputs instead of random noise. Strongly recommended whenever you're trying to refine or beat a specific existing attempt.
Score how far the kart has turned toward the reference ghost's own turn direction by this specific frame, not just at the end of the window. Motivated by watching a real reference already ~10 degrees rotated by frame 234, well before the window ends -- this adds a separate engine evaluation per candidate (cut at this frame), so it costs roughly double the per-iteration time. Requires "Reference .rkg" below. Empty = off (old behavior).
Extra reward for turning toward the reference's own direction by "Heading checkpoint frame" above. 0 = off.
Only used when "Score by" is "Progress". The ghost whose line you're trying to beat -- it's simulated once at the start to measure how far IT travelled, and candidates are scored by how far they travel in that same direction.
Where the reference ghost's own displacement is measured FROM (the frame cap above is the "to"). 172 = Countdown start, the earliest the kart can move under its own power anyway, so this rarely needs changing. For segment-chaining (see "Locked prefix .rkg" below), set this to the same frame as "Locked prefix length" so progress is scored only over the new segment.
Segment-chaining a long race (e.g. a full 3-lap run) piece by piece: point this at a PREVIOUS segment's winning result. Those frames are replayed verbatim every evaluation and never mutated -- this run's genome only searches the NEW frames from where that file ends (or "Locked prefix length" below, if set) through the Frame cap. Leave empty for a normal single-segment search (old behavior).
How many frames of "Locked prefix .rkg" to lock. Leave blank to lock its entire recorded sequence (the common case -- the whole previous segment).
Search start boost timing picks a single frame to start holding accelerate continuously through the rest of the attempt -- without it (or the two options below), accelerate is held the whole countdown, which always overshoots the boost charge (>0.95 = burnout) and guarantees no boost. This models a single clean hold; it can't represent tapping accelerate on and off, but converges fast since it's only one extra gene.

Search accelerate on/off channel and search wheelie (Trick::Up) channel each replace that single gene with a full channel (one on/off decision per control point, same spacing as steering), so real multi-tap patterns are reachable -- e.g. a technique that times a drift/hop or a wheelie into the corner, which the single-gene model can't reproduce at all. Confirmed necessary for at least one real reference ghost: its countdown movement couldn't be reproduced by steering + accelerate alone, but matched the real engine exactly once its actual wheelie taps were carried over. These cost a bigger search space (one more full channel each), so they take longer to converge and benefit even more from seeding. The accelerate channel takes priority over "search start boost timing" if both are checked.
